# Repos this project clones, and which ones need a fork you own

Audit date: 2026-08-30. Generated by inspecting `setup_third_party.sh`'s
real clone URLs and the actual `origin`/branch state of every checkout
under `third_party/`, not from memory.

`third_party/` is **gitignored** (`.gitignore:2`). Nothing under it is
stored in this repo. So for any checkout where this project has made its
own commits, exactly one of these must be true or the work is only on
this disk:

1. the checkout has a remote **you own** and the branch is pushed, or
2. the commits are captured in `third_party-patches/<name>.patch`, which
   `setup_third_party.sh` replays with `git am` after cloning upstream.

Both are legitimate. The failure mode is when neither holds, or when a
patch file silently drifts behind the checkout — which is exactly what
had happened to `PureDarwin.patch` (see Findings).

**59 repos total.** The main repo itself is `anurodhp/xnu-iokit-pi3`.

## 2. Upstream-only, but this project has committed to them

**This is the list that matters for your question.** Each carries
project-authored commits, has no fork you own, and is reproducible only
via its patch file. Forking these would let the work exist as real,
pushable branch history instead of a patch that can silently drift.

| Checkout | Upstream (read-only to you) | Project commits | Patch | Patch current? |
|---|---|---|---|---|
| `bash` | `apple-oss-distributions/bash` | 3 | `bash.patch` (1) | ❌ **DRIFTED** |
| `PureDarwin` | `PureDarwin/PureDarwin` | 6 | `PureDarwin.patch` (6) | ✅ (fixed 2026-08-30) |
| `swift-corelibs-foundation` | `apple/swift-corelibs-foundation` | 5 | `.patch` (3) | ✅ net-zero |
| `Csu` | `apple-oss-distributions/Csu` | 3 | `Csu.patch` (3) | ✅ |
| `ICU` | `apple-oss-distributions/ICU` | 3 | `ICU.patch` (3) | ✅ |
| `libdispatch` | `apple-oss-distributions/libdispatch` | 3 | `libdispatch.patch` (3) | ✅ |
| `cron` | `apple-oss-distributions/cron` | 2 | `cron.patch` (2) | ✅ |
| `BSM` | `apple-oss-distributions/BSM` | 1 | `BSM.patch` (1) | ✅ |
| `Libc` | `apple-oss-distributions/Libc` | 1 | `Libc.patch` (1) | ✅ |

"Patch current?" was verified the rigorous way, not by counting commits:
replay the patch with `git am` onto a detached worktree at the base
commit, then compare the resulting **tree hash** to the live checkout's.
`swift-corelibs-foundation` is marked net-zero because its two
uncaptured commits are a change and its own revert, so the end state
matches the patch exactly.

`setup_third_party.sh`'s own header explains the existing policy for
several of these — "no personal fork for a single commit each"
(`Csu.patch`, `Libc.patch`, `ICU.patch`, `BSM.patch`). That is a
reasonable call for a one-commit fix. It gets weaker as a checkout
accumulates commits: `PureDarwin` (6) and `bash` (3) are past the point
where a patch file is the low-risk option, and both are exactly where
drift actually happened.

## 3. Upstream-only, unmodified pins — no fork needed

The remaining ~45 checkouts are pinned to an exact tag and carry **no**
project commits, so there is nothing of yours to lose and a fork buys
nothing. They are re-clonable from upstream at any time:

`adv_cmds`, `awk`, `basic_cmds`, `cctools`, `CommonCrypto`, `copyfile`,
`diskdev_cmds`, `dyld`, `file_cmds`, `freebsd-src`, `gnudiff`, `gnutar`,

`OpenPAM`, `OpenSSH`, `removefile`, `shell_cmds`, `syslog`,

shallow/partial clones — it is upstream *release-tag* history that simply
isn't on a fetched remote-tracking branch, not project work. Don't treat
that number as a risk signal; check commit subjects.

## Findings / action items

1. **`bash.patch` has real drift — highest priority.** The checkout has 3
   commits; the patch captures only `smatch.c`. Missing are
   `9711c1d` (disable READLINE) and `ca6508d` (re-enable READLINE,
   disable `HAVE_TERMCAP_H`). These do **not** cancel out — verified by
   tree-hash replay. A fresh clone today builds a *different* bash, and
   per this project's own history that config is what fixed `bash -i`'s
   immediate-EOF-at-prompt bug. Fix:
   `cd third_party/bash && git format-patch <base>..HEAD --stdout >| ../../third_party-patches/bash.patch`
   then re-verify by replay.

2. **`PureDarwin.patch` was drifted; fixed 2026-08-30** (commit
   `1b83c24`). It captured 2 of 6 commits, so a fresh clone would have
   silently produced a launchd that still dies with the silent `exit(1)`.

3. **`dtc-AppleDeviceTree` and `u-boot` on-disk remotes don't match the
   script.** The checkouts point at `anurodhp/dtc-appledevicetree` and
   `anurodhp/u-boot`, but `setup_third_party.sh` still clones
   `darwin-on-arm/dtc-AppleDeviceTree` and `FlorentRevest/u-boot` and
   then applies a patch. A fresh clone therefore reproduces the *patched
   upstream*, not your fork. Not currently a correctness bug (the patch
   is the source of truth), but the two paths can diverge silently —
   worth deciding which is authoritative and making the script match.

4. **If you want forks for section 2**, the ones actually worth owning
   are `PureDarwin` and `bash` (most commits, both already drifted).
   `Csu`, `Libc`, `ICU`, `BSM` are single-commit fixes where the existing
   patch policy is fine.

5. **Re-run this audit after any third_party commit.** The check that
   matters is not "does a patch exist" but "does replaying it reproduce
   the current tree":

   ```
   git -C third_party/<repo> worktree add --detach /tmp/v <base>
   git -C /tmp/v am third_party-patches/<repo>.patch
   # compare: git -C /tmp/v rev-parse 'HEAD^{tree}'
   #     vs:  git -C third_party/<repo> rev-parse 'HEAD^{tree}'
   ```
